# RouteMap guide

RouteMap — первая вкладка Workspace и операторская мнемосхема маршрута. Она хранит
топологию, визуальные параметры и bindings в RouteMap definition, но не хранит
физические Modbus-адреса.

Пользовательский RouteMap definition хранится общим файлом
`%LOCALAPPDATA%\Configurator\RouteMap\route-map.json`. Runtime-выбор источника
`RouteMapRuntime.SignalSource` сохраняется в общем
`%LOCALAPPDATA%\Configurator\appsettings.json`, поэтому настройка mock/Modbus,
сделанная в admin, применяется и при следующем запуске в user.

## Основные файлы

| Область | Где лежит |
|---|---|
| Экран | `Configurator.Desktop/Workspace/RouteMap/RouteMapDashboardView.axaml` |
| Рисование карты | `Workspace/RouteMap/Controls/RouteMapControl.cs` |

| Runtime mapping | `Workspace/RouteMap/Services/RouteMapRuntimeMapper.cs` |
| Settings dialog | `Workspace/RouteMap/Settings/*` |
| JSON configuration | `Workspace/RouteMap/Configuration/*` |

## Definition

`RouteMapDefinition` описывает:

- логические размеры карты;
- цепочки маршрута;
- узлы;
- сегменты;
- attached-карточки оборудования;
- legacy-заявки и шаблоны заявок из seed;
- display settings и placeholder rules.

Актуальная версия пользовательского JSON — `schemaVersion = 22`.

```json
{
  "schemaVersion": 22,
  "map": {},
  "topBar": {},
  "chains": [],
  "nodes": [],
  "segments": [],
  "cards": [],
  "placeholderRules": []
}
```

JSON не сериализует Avalonia-типы. Цвета хранятся строками `#RRGGBB` или `#AARRGGBB`,
enum — строками, размеры и отступы — собственными DTO.

Цвета операторских кнопок TopBar и индикатора PowerStandby/кнопок `ПУСК`/`СТОП` карточки не входят в definition:
они фиксированы в UI для состояний normal, hover, pressed и checked. В JSON остаются
тексты кнопок, bindings и стили самой карточки.

## Узлы, линии и карточки

- Узлы создаются с `id`, `title`, координатами, kind, label placement, menu kind,
  static visibility и bindings.
- Линии ссылаются на `fromNodeId` и `toNodeId`; поддержаны `Straight` и `RoundedElbow90`.
- Длинные линии могут иметь `ActiveRouteFragment` bindings вида
  `route.<segmentId>.fragment_<n>.active`.
- Карточки оборудования содержат status text, start/stop commands, параметры
  оборудования, стили и привязку к цепочке или vertical anchor.

Линии не selectable: hit-test возвращает узлы и runtime-объекты, но не сегменты.
Не добавляйте selection для линий без отдельного изменения hit-test, marker rendering и тестов.

## Runtime state

RouteMapRuntimeMapper применяет сигналы к объектам. Для узлов, линий и карточек
без таблицы технологических статусов действует общий приоритет состояния.

```text
Offline -> Disabled -> Fault -> ActiveRoute -> static fallback
```

PLC-mapped `system.fault=true` переводит все runtime-объекты RouteMap в тот же `Fault`-вид,
что и локальная роль `Fault=true`; `Offline`/bad quality остаются выше по приоритету.

`Visible=false` скрывает объект. `Fault=true` перекрывает active route. Bad quality или
stale по активному сигналу переводят объект в `Offline`.

Опциональная роль `Enabled` доступна для узла, линии, карточки, кнопок `СБРОС` и `АВАРИЯ`.
Это `Read/Bool`: хорошее значение `false` дает состояние `Disabled`, блокирует ввод и
использует темно-серый `Map.Palette.Disabled`; отсутствие binding или значения оставляет
элемент доступным. Bad/stale сохраняет обычное состояние `Offline`.
Для карточки `Enabled=false` отключает визуал, `ПУСК` и `СТОП`, но не управляет
кнопкой `Н`: она доступна без подключения в обоих режимах. Для карточки с
`PowerFeedback` индикатор питания остаётся только отображением; `Enabled=false`
не порождает selector-записей.

Системный `connection.connected=false` означает недоступную Modbus-связь: mapper
форсирует `Offline` для всех узлов и линий, а карточки показывают текст `Не в сети`
серым индикатором и блокируют команды независимо от status/text binding. Кнопка `Н`
остается доступной: editable-значения можно сохранить локально и без PLC.
Выбранные роли `IsTarget`/`IsLoader` продолжают визуально выделять узел до снятия роли.

### Технологические статусы карточки

Опциональный объект `cards[].statusMapping` связывает код PLC с подписью и цветом
строки и кружка статуса. Код читается из существующей привязки `Text` с направлением
`Read` и типом `UInt16` или `Word`. У «Кюбель Л.К.» это `equip.bucket.text`.
Карточка без таблицы использует прежнее чтение `Text` и резервный `statusText`.

| Поле | Допустимые значения и назначение |
|---|---|
| `entries` | От 1 до 256 записей. |
| `code` | Уникальное в пределах карточки целое число от 0 до 65535. |
| `text` | Подпись статуса, от 1 до 100 символов. |
| `color` | Цвет подписи и кружка в формате `#RRGGBB` или `#AARRGGBB`. |
| `category` | `normal`, `information`, `warning`, `fault` в JSON. Категория участвует в диагностике и вычислении состояния. |
| `blockStart`, `blockStop` | Независимые дополнительные запреты ПУСК и СТОП. У записи `fault` оба флага обязательны и равны `true`. |
| `unknownText` | Текст для полученного кода, которого нет в таблице. UI добавляет «(код N)». |
| `unavailableText` | Текст для отсутствующего, недостоверного, устаревшего значения или неверного типа. |

Оба резервных текста обязательны и содержат до 100 символов. Типизированное
runtime-представление хранит код, категорию, качество, цвет и запреты. Подсказка
показывает SignalId, полученный код, причину текущей индикации и запреты по статусу.

Для карточки с таблицей применяется следующий порядок.

1. `Offline` перекрывает другие состояния. При недоступной связи или срабатывании
   общего правила Offline по другим bindings карточка показывает «Не в сети».
   Если в Modbus runtime не осталось работающих ролей, адаптер ждёт новый снимок
   перед восстановлением качества.
   Если источник передал `null` вместо снимка, UI также показывает Offline.
2. `system.fault=true` или локальный `Fault=true` показывают «Авария системы» или
   «Авария оборудования» в цвете `Map.Palette.Fault`. Запись категории `fault`
   показывает собственные текст и цвет. Авария имеет приоритет над `Disabled`.
3. `Enabled=false` приглушает неаварийную подпись цветом `Map.Palette.Disabled`.
4. Для неизвестного кода используется `Map.Palette.Warning`, для недостоверного
   `Text` — `Map.Palette.MutedText`. Для остальных кодов берутся текст и цвет из записи.

Технологический статус описывает код оборудования. Общий `RouteObjectState`
отражает доступность и состояние объекта на карте. Для карточек с таблицей статус
может дать `Fault`, `Warning` или `Unknown` с учётом перечисленных приоритетов.
PowerStandby по-прежнему получает состояние питания из `PowerFeedback`.

Авария, Offline, Disabled, неизвестный код и недостоверный `Text` блокируют обе
кнопки. Для достоверных неаварийных записей флаги добавляют запреты к имеющимся
ограничениям связи, доступности, feedback и команд. Обновление статуса не вызывает
запись. PLC определяет физические разрешения, межблокировки и безопасность.

## Команды

### Верхняя панель

В `Application.WorkMode=admin` кнопки по умолчанию идут в порядке
**ВЫГРУЗКА → ВРАЩЕНИЕ → ЗАГРУЗКА → СБРОС → АВАРИЯ → НАСТРОЙКИ**.
При нехватке места прокручивается центральная группа. «ПРОМ Диспетчер» остаётся
слева, `ПОМОЩЬ` — справа. В `user` остаются `СБРОС`, `АВАРИЯ` и `ПОМОЩЬ`.
`ВЫГРУЗКА`, `ВРАЩЕНИЕ`, `ЗАГРУЗКА` и `НАСТРОЙКИ` скрыты, а `TopBarViewModel`
блокирует прямой вызов каждой из трёх новых команд в `user`.
`Application.WorkMode` задаёт режим интерфейса и программный допуск в приложении.
Защищённая аутентификация этим режимом не обеспечивается. Физические разрешения
на выполнение и межблокировки определяет PLC.

| Текст по умолчанию | Секция `topBar` | Роль C# | SignalId по умолчанию |
|---|---|---|---|
| `ВЫГРУЗКА` | `unload` | `UnloadCommand` | `system.command.unload` |
| `ВРАЩЕНИЕ` | `rotation` | `RotationCommand` | `system.command.rotate` |
| `ЗАГРУЗКА` | `load` | `LoadCommand` | `system.command.load` |

Все три — моментальные `Button` для `admin` с обязательной привязкой `ReadWrite/Bool`
и режимом `Pulse` в `Modbus.DataMap`. Команде нужен свежий `connection.connected=true`
с качеством `Good`. Если настроен `Enabled`, требуется также его свежий `Good/true`.
`false`, отсутствующее значение, Bad/Stale или неверный тип настроенного `Enabled`
блокируют связанную кнопку. Без `Enabled` доступность определяется остальными
условиями. Во время отправки повтор той же команды блокируется. В Modbus-режиме
отсутствующая или несовместимая точка также блокирует команду. Обновление снимка
меняет доступность без отправки этих команд.

Ниже показан фрагмент JSON с новыми секциями. В полном документе сохраняются
`automatic`, `manual`, `reset`, `emergency` и остальные данные карты, включая
пользовательские тексты и привязки. Имена ролей в JSON используют camelCase.

```json
{
  "topBar": {
    "unload": {
      "text": "ВЫГРУЗКА",
      "bindings": [{ "role": "unloadCommand", "signalId": "system.command.unload", "direction": "readWrite", "valueType": "bool" }]
    },
    "rotation": {
      "text": "ВРАЩЕНИЕ",
      "bindings": [{ "role": "rotationCommand", "signalId": "system.command.rotate", "direction": "readWrite", "valueType": "bool" }]
    },
    "load": {
      "text": "ЗАГРУЗКА",
      "bindings": [{ "role": "loadCommand", "signalId": "system.command.load", "direction": "readWrite", "valueType": "bool" }]
    }
  }
}
```

### Карточки и существующие команды

Карточка «Кюбель Л.К.» использует `equip.bucket.power` (`PowerFeedback`,
`Read/Bool`), `equip.bucket.start` (`StartCommand`, `ReadWrite/Bool/Pulse`) и
`equip.bucket.stop` (`StopCommand`, `ReadWrite/Bool/Latched`). PowerStandby размером
40×40 — неинтерактивный индикатор: хороший свежий `false` даёт красный `#D10000`,
`true` — зелёный `#00D107`; missing/Bad/Stale/offline или неверный тип дают
нейтральный серый и подсказку о неизвестном состоянии. Клик, клавиши, readback и
`Enabled=false` не отправляют запись от индикатора. Адрес питания задаётся вручную:
старый writable selector не является доказанным физическим feedback.

`ПУСК` — моментальная `Button`: одно действие передаёт только `StartCommand=true`.
Modbus dispatcher выполняет один Pulse `true → delay → false` с настроенным
`PulseDurationMs` (default 300 мс). Отпускание указателя не пишет `false`;
повторное нажатие не накладывает второй импульс. При неопределённом исходе `true`
делается ограниченная попытка `false`, ошибка видна оператору. `ПУСК` не снимает
`СТОП`; факт работы привода определяется отдельным PLC feedback.
Если сохранённый `Modbus.DataMap` задаёт Start не как Pulse, команда отклоняется до записи;
оператор видит ошибку и должен исправить mapping.

`СТОП` остаётся `ToggleButton`: checked пишет только `StopCommand=true`, unchecked —
только `StopCommand=false`. Финальное положение берётся из хорошего свежего readback;
ожидание снимает достоверное значение самой привязки `StopCommand`, совпавшее с запросом.
Для подтверждения недостаточно сброса checked от `StopOffFeedback` или недоступности значения.
Snapshot не инициирует обратную запись. Ошибка записи/подтверждения отображается.
Если свежий readback не подтверждает запрошенное положение за 10 секунд, ожидание
снимается с видимой ошибкой; автоматического повтора записи нет. Stop с режимом
записи не Latched отклоняется до записи.
Это обычная программная команда, не аварийный останов и не PLC interlock.
`АВАРИЯ`, `TargetCommand` и `LoaderCommand` сохраняют прежнюю семантику.

`СБРОС` — отдельная моментальная команда `system.reset` с ролью `ResetCommand`:
`ReadWrite/Bool`, режим записи Modbus `Pulse`, не `Latched`. При нажатии UI отправляет
только `true` и не пишет `false` при отпускании. Modbus dispatcher завершает импульс
записью `false` после `PulseDurationMs`. Кнопка временно показывает активное состояние
во время отправки и учитывает последующий readback; подробности — в [гайде Modbus TCP](03-modbus-tcp-guide.ru.md).
`АВАРИЯ` (`EmergencyCommand`, по умолчанию `system.emergency`) сохраняет семантику
`ToggleButton` с `true/false` и `Latched` в штатной карте Modbus.

Исторические карточки без `PowerFeedback` сохраняют прежнюю selector-семантику для
совместимости JSON; новые и мигрированные карточки «Кюбель Л.К.» её не используют.
Режимы `АВТОМАТ` и `РУЧНОЙ` скрыты в user/admin TopBar и редакторе настроек, их
команды инертны, а SignalId исключены из активного inventory. Legacy-поля TopBar
сохраняются при чтении и сохранении старого JSON.

`StartOffFeedback` и `StopOffFeedback` снова являются активными ролями карточек. Это
`Read/Bool` сигналы: `true` отключает соответствующую кнопку; для исторических
Toggle-карточек также снимает checked без обратной записи в PLC. Остальные `*OffFeedback` и `State`
остаются legacy.

Кнопка `Н` в заголовке карточки открывает модальный диалог параметров оборудования.
Ее доступность не зависит от binding-регистра `Enabled` и от подключения в обоих режимах.
В модели `EquipmentCardParameter` хранит название, сигнальную привязку с ролью
`EquipmentParameter` и свойство `Visibility`. Редактируемые параметры также хранят локальную уставку,
статус ожидающей автоотправки и последнюю ошибку. При открытии `Read` получает последнее
хорошее runtime-значение, а `Write`/`ReadWrite` используют сохранённый setpoint, если он
есть.
Bool-параметры вводятся переключателем `Вкл/Выкл`; числовые и строковые параметры
валидируются по `ValueType`, включая `WORD`, `DWORD` и `DATE`. В admin-режиме диалог
показывает техническую подпись `SignalId • Type`; в user-режиме она скрыта. `Сохранить`
без подключения сохраняет валидные `Write`/`ReadWrite` значения в `route-map.json` без
проверки Modbus mapping и помечает их ожидающими. При первом reconnect Modbus каждое
ожидающее значение отправляется один раз; успех или ошибка снимают ожидание, а ошибка
видна в диалоге. Онлайн-сохранение сохраняет значение и использует обычную проверку
mapping/`SignalWriteRequest`; ручное `Сохранить` создаёт новую попытку.

Поле `cards[].parameters[].visibility` задаёт видимость строки в операторском
диалоге по режиму `Application.WorkMode`.

| Значение JSON | Вариант в редакторе | Диалог в `user` | Диалог в `admin` |
|---|---|---|---|
| `user` (`EquipmentParameterVisibility.User`) | Для пользователя | Видна | Видна |
| `admin` (`EquipmentParameterVisibility.Admin`) | Только для администратора | Скрыта | Видна |

Диалог фильтрует параметры до создания строк и сохраняет исходный порядок.
`Сохранить` обрабатывает только видимые редактируемые строки. Если видимых строк
нет, диалог показывает «Для текущего режима нет доступных настроек оборудования.»,
отключает `Сохранить` и оставляет доступной кнопку `Закрыть`.

## Правая панель

RouteMap справа показывает `NotificationsPanelView`: вкладка `Уведомления` держит
минимальную ширину `400`, а при открытии `Истории` правая колонка расширяется по ширине
таблицы журнала.
Вкладка `Уведомления` отображает тревоги из `Modbus.AlarmMap` после показа диалога:
один элемент на `AlarmMap.Id`, дата/время берутся с фронта `Alarm=false -> true`.
Элемент повторяет стиль диалога, открывает диалог по нажатию, а кнопка `X` удаляет его
только когда текущий alarm-бит уже `false`. Нижняя кнопка `Очистить список` применяет
то же правило ко всем элементам: активные тревоги остаются в списке.

Вкладка `История` показывает последние 1000 событий текущего запуска и доступна в режиме
`admin`. Журнал регистрирует завершившиеся отправки `SignalId`, первые и изменённые
достоверные значения из `Modbus.DataMap`, а также активацию, снятие и локальное `OK` тревог.
Фоновая запись в SQLite работает в обоих режимах приложения. Настройки периодической
и ручной архивации в ZIP находятся во вкладке `Настройки приложения`.
Направление показывается стрелкой: `↓` для полученных/входящих событий,
`↑` для отправленных команд и `OK`. `Роли` и `Объекты` отображаются одним столбцом как в
`SignalId ↔ Modbus`; `Адрес` показывает только zero-based offset без имени area.
Операторские тревоги не становятся `SignalId` и не переносятся в `Modbus.DataMap`.

### Архивация истории

Откройте `Настройки приложения` → `Архивирование истории Route Map`. Выберите интервал
и папку для ZIP, затем нажмите `Сохранить настройки`. Пустое поле папки выбирает
каталог `history/archives` в профиле пользователя. Кнопка `Архивировать сейчас`
доступна и при выключенном расписании. Блок состояния показывает последний архив,
следующую попытку, очередь записи, число непринятых событий и последнюю ошибку.

Фоновый писатель сохраняет события по мере поступления транзакциями до 200 записей.
Архиватор читает из `events.db` уже сохранённые события после последнего подтверждённого
ID и до зафиксированной верхней границы. ZIP содержит `events.jsonl` и `manifest.json`.
В манифесте записаны границы ID, число событий, даты в UTC и SHA-256 содержимого
`events.jsonl`. Курсор БД продвигается после проверки и публикации ZIP.

При штатном закрытии журнал завершает запись очереди, затем приложение пытается
создать ZIP, если включены расписание и архивация при закрытии. При аварийном
завершении события в очереди до коммита SQLite могут потеряться. Пути, значения
по умолчанию и правила очистки описаны в [гайде по хранению данных](09-configuration-file-locations.ru.md).

## Редактор

Кнопка `НАСТРОЙКИ` открывает `RouteMapSettingsDialog`. В режиме
`Application.WorkMode=user` кнопка скрыта, а Workspace показывает только RouteMap.
При этом скрытие настроек не меняет сохраненную конфигурацию: user продолжает читать
общие `RouteMapRuntime`, `Modbus` и `ModbusDemo`, но не показывает вкладки настройки,
включая admin-вкладку `Менеджер тревог`. User-режим при этом продолжает реагировать на
`Modbus.AlarmMap`.
В этой карте `Alarm area/Offset/Bit` задают входной бит диалога, `OK area/Offset/Bit` —
отдельный бит подтверждения, `Repeat ms` — повтор при активном alarm-бите, `Pulse ms` —
длительность acknowledgement-импульса.
Вкладки:

- `Источник данных`;
- `Карта и маршруты`;
- `TopBar`;
- `Узлы`;
- `Линии`;
- `Карточки`;
- `Заглушки`.

Откройте `НАСТРОЙКИ` → `TopBar`. В секциях `ВЫГРУЗКА`, `ВРАЩЕНИЕ` и `ЗАГРУЗКА`
поле `Текст` задаёт подпись кнопки, а в таблице `Signal bindings` редактируется
`SignalId`. Основная командная строка обязательна и не удаляется. `Добавить binding`
создаёт один необязательный `Enabled` с `Read/Bool` и начальным SignalId
`<commandSignalId>.enabled`. Его SignalId можно изменить, а строку убрать кнопкой
`Удалить`. Применение и сохранение настроек TopBar обновляют команды и инвентарь
без отправки этих команд или назначения физических адресов. `ЗАКРЫТЬ` отбрасывает
изменения, оставшиеся только в черновике.

Во вкладке `Карточки` администратор настраивает список параметров оборудования:
добавляет/удаляет строки, задает название, единственную роль `EquipmentParameter`,
`SignalId`, `Direction` и `ValueType`. В секции «Настройки оборудования» столбец
«Отображать для» задаёт `Visibility` каждой строки. Редактор показывает все строки,
а новая строка получает «Для пользователя». Дубликат карточки наследует видимость
каждого параметра. Для редактируемых строк RouteMap также сохраняет
последний локальный setpoint, pending-статус и ошибку отправки. Изменение `SignalId`,
`Direction` или `ValueType` очищает эти данные; дублирование карточки их не копирует.
При изменении только `Visibility` сигнальная привязка, `SavedValue`,
`PendingAutoDispatch` и `LastDispatchError` сохраняются. Полное определение карты,
список `SignalId ↔ Modbus` и `EquipmentParameterAutoDispatcher` используют параметры
обеих категорий. Физические адреса по-прежнему задаются в `Modbus.DataMap`, а решение
о выполнении команд принимает ПЛК. Новые параметры по умолчанию получают тип `Word`; старые
`UInt16` остаются валидными и совместимыми.

Новые и мигрированные карточки с моментальным Start содержат `PowerFeedback` с
`<cardId>.power` без автоматического назначения физического адреса. Старые selector
bindings не возвращаются для «Кюбель Л.К.». Миграция `v12 -> v13` добавляет TopBar
`СБРОС` с обязательным `ResetCommand` и SignalId `system.reset`. `Enabled` остается
опциональным и добавляется администратором. На действующих кнопках TopBar
опциональный `Enabled` можно добавлять и удалять, а основной command-binding
остаётся обязательным. Исторические `Automatic/Manual` редактированию не подлежат.

`ПРИМЕНИТЬ` валидирует и публикует definition без записи файла. `СОХРАНИТЬ` валидирует,
атомарно сохраняет JSON и публикует definition. Невалидный документ не публикуется.

В режиме `admin` откройте `Карточки → Технологические статусы` и включите
«Использовать таблицу статусов». Для `equip.bucket` редактор создаёт шесть начальных
строк, для других карточек нужно добавить хотя бы одну. Изменения строк и резервных
текстов остаются в черновике до применения или сохранения. Дублирование создаёт
отдельную копию таблицы. В режиме `user` сохранённая таблица участвует в расчёте статуса.

## Миграции и validation

Перед validation документ проходит `RouteMapConfigurationMigrator`. Validator проверяет
schema version, уникальность ID, ссылки, роли bindings, обязательные команды, параметры
карточек, геометрию, цвета, fragment bindings, placeholder rules и toggle-семантику
команд.

Миграция `v17 → v18` добавляет таблицу только для `equip.bucket` с совместимой
привязкой `Text`, если таблицы ещё нет. Коды 0–5 получают подписи «Выключен»,
«Ожидание», «Авария», «Выполнение», «Выгрузка», «Загрузка». Цвета берутся из
сохранённой палитры `MutedText`, `Warning`, `Fault` и `Ready`. Остальная конфигурация
карты и локальные уставки сохраняются. Повторное открытие v18 использует сохранённую
таблицу как есть.

Миграция `v18 → v19` сохраняет узлы, линии, координаты и привязки. В v19 линия
`deadEnd` связывает обычный узел с `terminalAnchor`. Поле `terminalSide` указывает
на сторону якоря (`from` или `to`), а необязательное `terminalCapLength` задаёт
длину поперечины в логических единицах. Якорь без ролей и привязок принадлежит
одной линии. Привязки линии относятся к её основному участку.

Миграция `v19 → v20` обновляет прежнюю штатную цепочку `chain.bucket_route`,
если совпадают ID и направленные связи и у старых тупиков нет пользовательских
зависимостей. Она добавляет МОЙКУ в прежней позиции верхнего круглого тупика,
преобразует оба тупика в терминальные якоря и сохраняет сигналы и фрагменты
существующих линий. Перед сохранением активного файла создаётся резервная копия.
У двух штатных тупиков подписи выводятся у поперечин. Пользовательские тупики
сохраняют позиционирование подписей вдоль линий.

МОЙКА использует `route.node.wash.target` (ReadWrite Bool, для Modbus требуется
Latched) и `route.node.wash.active` (Read Bool). Для работы с ПЛК нужны согласованные
привязки в `Modbus.DataMap`. При отсутствующей или несовместимой привязке команды
прежняя точка назначения сохраняется и отображается ошибка.

Миграция `v20 → v21` добавляет `visibility: "user"` параметрам без этого поля
и сохраняет явно заданное допустимое значение, существующие уставки и
дополнительные поля JSON. Менеджер создаёт резервную копию исходного активного файла
и атомарно сохраняет результат. Явное некорректное значение `visibility` вызывает
ошибку загрузки или валидации.

Миграция `v21 → v22` добавляет отсутствующие или `null`-секции `unload`, `rotation`,
`load` со штатными значениями и сохраняет уже настроенные секции, `reset`, `emergency`
и исторические `automatic`/`manual`. Тесты миграции и сохранения с повторным открытием,
экспортом и импортом подтверждают сохранность пользовательских текстов, SignalId,
`Enabled` и дополнительных JSON-полей на уровне документа, `topBar`, кнопки и binding.
Загрузка v22 также подставляет отсутствующие секции в памяти, не переписывая файл.
Если секция существует, но её обязательный binding отсутствует, валидатор отклоняет
документ. При успешной миграции активного файла менеджер сохраняет резервную копию
оригинала и обновляет JSON.

Не обходите manager и validator прямыми изменениями UI state.
