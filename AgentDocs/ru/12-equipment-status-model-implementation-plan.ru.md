# PromFlow.Dispatcher — план реализации конфигурируемой модели технологических статусов

**Целевая ветка:** `17-demo-v2` репозитория `zdanilv/PromFlow.Dispatcher`  
**Исходная схема Route Map:** `schemaVersion = 17`  
**Целевая схема:** `schemaVersion = 18`  
**Область изменений:** статусы карточек оборудования Route Map; пилотная и обязательная для миграции карточка `equip.bucket` («Кюбель Л.К.»).  
**Статус реализации:** не начата.

## 1. Цель и границы изменений

### 1.1. Требуемый результат

Реализовать для карточек оборудования самостоятельную, редактируемую в административном UI модель технологических статусов, которая:

1. Принимает числовой код от существующего `Text`/`SignalId` binding (для «Кюбель Л.К.» — `equip.bucket.text`, `Read`, `UInt16`).
2. Находит код в таблице записей карточки; каждая запись отдельно хранит **код**, **подпись**, **цвет**, **диагностическую категорию** и **два запрета команд** (`blockStart`, `blockStop`).
3. Передаёт в runtime типизированный результат (известный код, неизвестный код, отсутствие/ошибка данных, внешняя авария, отключённая связь), а не вычисляет цвет сопоставлением русской строки.
4. Отображает оператору статус согласованно с `Offline`, `Fault`, `Disabled`, `PowerFeedback`, `Enabled` и `system.fault`, не показывая «Выключено» при неизвестном или повреждённом коде.
5. Учитывает блокировки **только как дополнительные UI-запреты**: настройки статуса никогда не могут разрешить команду, уже запрещённую действующими проверками Route Map или PLC.
6. Сохраняет полный цикл `редактор → JSON → миграция → validation → definition → runtime → карточка`, включая импорт/экспорт и тесты.
7. Безопасно обновляет существующие пользовательские документы v17 на v18, не изменяя фактические адреса Modbus, `SignalId`, команды и setpoint-данные.

### 1.2. Ограничения области работ

- **Не менять** логику безопасности PLC, проект контроллера, PLC-программу и физические адреса полевых устройств.
- **Не выполнять** реальных Modbus-команд, alarm ACK или подключения к производственному endpoint. Верификация — тестовые SignalValue, Mock, loopback и существующие unit/headless UI tests.
- **Не менять** транспортный Modbus runtime, `Modbus.DataMap`, `Modbus.AlarmMap`, `ModbusDemo.DataMap`, адреса HR 37/58, настройки автозапуска и протокол записи без доказанной необходимости. Расхождение HR 37 / `ПК_СТАТУС_КЮБЕЛЬ` HR 58 остаётся отдельным вопросом PLC-контракта, не автоматической правкой.
- **Не менять** семантику `ПУСК` (Momentary + Pulse), `СТОП` (Toggle + Latched/readback), PowerStandby (read-only), параметров оборудования и выбора маршрута.
- **Не расширять** конфигурируемую модель статусов на узлы, линии, TopBar, OPC UA и менеджер тревог. Для них сохранить существующую обработку.
- **Не создавать** новую транспортную подсистему, отдельный справочник Modbus-адресов или новый механизм авторизации.
- Сохранить текущие пользовательские настройки, пользовательские файлы и порядок `Apply`/`Save`. Не переписывать исходный файл из приложенного примера и не менять настройки на работающем объекте.

### 2.2. Требования совместимости с существующим поведением

- `Text` для `equip.bucket` сейчас указывает на `equip.bucket.text` (`Read/UInt16`). В предоставленном Modbus-профиле это HR offset 37; изменение адреса **не входит** в работу.
- Текущие коды: `0 Выключен`, `1 Ожидание`, `2 Авария`, `3 Выполнение`, `4 Выгрузка`, `5 Загрузка`. Их подписи, исходные цвета и коды должны пережить миграцию без изменения.
- Текущий `statusText = "Выключено"` сохранить как legacy-резервное поле, но для карточки с включённой новой таблицей не использовать для неизвестного кода.
- Для карточек **без** `statusMapping` сохранить старое поведение, включая legacy текстовый binding. Новую строгую логику применять только к карточкам с настроенной моделью.
- Системные `connection.connected` (создаётся runtime) и `system.fault` (PLC-mapped) остаются на прежних местах. `Status` не заменяет ни один из них.
- Существующие `StartOffFeedback`, `StopOffFeedback`, `Enabled`, `PowerFeedback` продолжают действовать. Никакого автоматического `write` при переходе статуса, получении snapshot, миграции или открытии UI.

## 3. Целевая модель статусов: контракт v18

### 3.1. Расширение JSON карточки

Добавить **необязательное** свойство `statusMapping` в `cards[]`. `null` или отсутствие поля означает legacy-режим без включённой таблицы. Для `equip.bucket` миграция v17→v18 добавляет таблицу автоматически.

Рекомендуемый и фиксируемый в реализации контракт:

```json
{
  "schemaVersion": 18,
  "cards": [
    {
      "id": "equip.bucket",
      "statusText": "Выключено",
      "statusMapping": {
        "unknownText": "Неизвестный статус",
        "unavailableText": "Нет достоверного статуса",
        "entries": [
          { "code": 0, "text": "Выключен", "color": "#77828D", "category": "normal", "blockStart": false, "blockStop": false },
          { "code": 1, "text": "Ожидание", "color": "#D99B22", "category": "information", "blockStart": false, "blockStop": false },
          { "code": 2, "text": "Авария", "color": "#D95D4E", "category": "fault", "blockStart": true, "blockStop": true },
          { "code": 3, "text": "Выполнение", "color": "#3A9D5D", "category": "information", "blockStart": false, "blockStop": false },
          { "code": 4, "text": "Выгрузка", "color": "#3A9D5D", "category": "information", "blockStart": false, "blockStop": false },
          { "code": 5, "text": "Загрузка", "color": "#3A9D5D", "category": "information", "blockStart": false, "blockStop": false }
        ]
      }
    }
  ]
}
```

Это **фрагмент**, а не файл, пригодный для замены реального `route-map.json`: все остальные свойства, другие карточки и разделы должны сохраняться.

### 3.2. Семантика полей

| Поле | Тип / допустимые значения | Назначение |
|---|---|---|
| `statusMapping` | объект или отсутствует | Включает таблицу только на данной карточке |
| `entries` | массив из 1–256 записей | Соответствия числовых кодов |
| `code` | целое `0..65535` | Ключ чтения `UInt16`/`Word`; уникален в пределах карточки |
| `text` | непустая строка, ≤100 символов | Точный текст операторской строки |
| `color` | `#RRGGBB` или `#AARRGGBB` | Цвет именно технологической подписи/кружка; не глобальная палитра |
| `category` | `normal`, `information`, `warning`, `fault` | Типизированная диагностическая категория; **не** текст и **не** цвет |
| `blockStart` | bool | Дополнительный запрет операционной команды «ПУСК» для этого кода |
| `blockStop` | bool | Дополнительный запрет операционной команды «СТОП» для этого кода |
| `unknownText` | непустая строка, ≤100 символов | Основная часть текста при полученном, но не описанном числовом коде; показывать также число |
| `unavailableText` | непустая строка, ≤100 символов | Текст при отсутствующем / недостоверном значении |

Ни одна категория и ни одно поле `block* = false` не отменяют более сильные запреты. `category = fault` принудительно создаёт аварийное состояние карточки и запрещает обе команды даже при `blockStart=false` или `blockStop=false`: эти флаги в данном случае избыточны. Редактор должен показывать этот смысл; валидатор **требует** оба `block* = true` для `fault`, чтобы конфигурация не вводила администратора в заблуждение. Для `normal`, `information`, `warning` поля независимы и задают дополнительные запреты.

### 3.3. Типы C# (предлагаемые имена)

1. `EquipmentStatusCategory`: `Normal`, `Information`, `Warning`, `Fault`.
2. `EquipmentStatusEntry`: `Code`, `Text`, `Color`, `Category`, `BlockStart`, `BlockStop`.
3. `EquipmentStatusMapping`: `Entries`, `UnknownText`, `UnavailableText`.
4. `EquipmentStatusQuality`: `Known`, `UnknownCode`, `Missing`, `BadOrStale`, `WrongType`, `Disconnected`, `ForcedFault` (или отдельные typed flags с эквивалентной семантикой).
5. `EquipmentStatusPresentation` (readonly record): `Code?`, `Text`, `Color`, `Category?`, `Quality`, `BlockStart`, `BlockStop`, `IsTrusted`, `DiagnosticText`.
6. DTO-аналоги в `RouteMapConfigurationDocument.cs`, пригодные для JSON и привязки редактора; изменяемые строки DTO должны уведомлять VM об изменениях.

Доменные типы модели и DTO не должны ссылаться на Avalonia Brushes. Цвет в них — обычная валидированная строка. Runtime-представление **не сериализуется** в Route Map.

### 3.4. Источник кода и типизация

- Использовать **существующий** binding с ролью `Text` для карточки: новый binding/SignalId не вводить.
- При наличии `statusMapping` `Text` обязателен, `Direction = Read`, `ValueType = UInt16` либо `Word` (совместимость для вновь создаваемых Word-карт); на уровне Modbus должна использоваться совместимая числовая точка.
- В `EquipmentStatusResolver` допустимы только корректные беззнаковые значения диапазона `0..65535` из достоверного runtime signal. Не приводить произвольную строку и отрицательное число к валидному коду; такие данные имеют `WrongType`.
- Для `statusMapping = null` оставить текущий `ReadText` и его поддержку строк/чисел на legacy-карточках.
- Не превращать неподдерживаемые строки, `null`, повреждённые или просроченные значения в код `0`.

## 4. Однозначные правила вычисления и приоритета

### 4.1. Расчёт технологического статуса

1. Нет `connection.connected` или он сообщает об отказе/Bad/Stale: действующий механизм определения доступности применяется как прежде. Если соединение **явно недоступно**, `Disconnected`: видимый текст строго `«Не в сети»`, серый индикатор, ПУСК/СТОП запрещены.
2. У активного `Text` нет значения в snapshot: `Missing`; показывать `unavailableText`, качество неизвестно, ПУСК/СТОП запрещены.
3. `Text.IsQualityGood = false` или `IsStale = true`: `BadOrStale`; показывать `unavailableText`, ПУСК/СТОП запрещены.
4. Тип значения неверен: `WrongType`; показывать `unavailableText` с диагностикой типа, ПУСК/СТОП запрещены.
5. Значение корректно, но кода нет в `entries`: `UnknownCode`; показывать `«{unknownText} (код N)»`, предупреждающий цвет (`palette.warning`), ПУСК/СТОП запрещены. Нельзя подменять «Выключено».
6. Значение известно: `Known`, брать подпись, цвет, категорию и поля запрета **из соответствующей записи**, без сравнения текста со строковыми литералами.

`UnknownCode` диагностически отличен от потери связи: предупреждающий статус и известное числовое значение сохраняются в runtime; `Missing`, `BadOrStale`, `WrongType` — недостоверные данные. Разница должна быть видна в подсказке и тестах.

### 4.2. Наложение аварий и доступности

Для карточки **с** `statusMapping` использовать в вычислении операторского представления приоритет:

1. **Disconnected** / явный `Offline` — показывать «Не в сети» или «Нет достоверного статуса»; не считать старый полученный код актуальным.
2. **Global/local fault** — если `system.fault = true` или настроенный для карточки `Fault` binding = true, показать `«Авария системы»` / `«Авария оборудования»` красным цветом `palette.fault`, состояние `Fault`, запретить ПУСК/СТОП. Сохранять последний доверенный код лишь для диагностической подсказки, но не продолжать показывать «Выполнение» зелёным.
3. **Mapped category = fault** — отображать текст записи («Авария»), её красный цвет, состояние `Fault`, запретить обе команды.
4. **Enabled = false** — состояние `Disabled`, запретить обе команды. Подпись известного неаварийного статуса остаётся различимой, но приглушённой; авария из п. 2–3 визуально имеет приоритет над серым Disabled.
5. **UnknownCode** — предупреждение, запретить обе команды.
6. **Mapped warning** — предупреждающая диагностическая категория; запреты определяются `blockStart` / `blockStop` в дополнение к существующим условиям.
7. **Mapped normal/information** — цвет и текст из записи; при отсутствии указанных запретов применяются существующие правила команд.

Это **локальная политика карточек с новой таблицей**. Не менять установленный приоритет состояния узлов, линий и карточек без `statusMapping`; если переработка общей функции `MapObject` необходима, защитить старое поведение отдельными регрессионными тестами.

### 4.3. Итоговые разрешения команд

После расчёта существующих `CanStart`/`CanStop` применять только пересечение с новыми разрешениями:

```text
FinalCanStart = ExistingCanStart AND TrustedStatus AND NOT StatusBlockStart
FinalCanStop  = ExistingCanStop  AND TrustedStatus AND NOT StatusBlockStop
```

При `Fault`, `Offline`, `Disabled`, `UnknownCode`, `Missing`, `BadOrStale`, `WrongType` оба результата `false` независимо от сохранённых `block*`. Для доступного известного кода `category != fault` дополнительные запреты берутся из записи. Нельзя через настройку статуса переопределить `StartOffFeedback`, `StopOffFeedback`, connection gate, глобальную аварию, `canStart/canStop` или readback-подтверждение. Запреты не должны сами посылать `false`, `true` или reset в PLC.

**Важно:** `СТОП` здесь программная Toggle-команда, не аппаратный аварийный останов. Требования безопасности и физические межблокировки остаются на стороне PLC.

### 4.4. Результат на панели оператора

- Строка статуса и кружок получают `Text`/`Color` из `EquipmentStatusPresentation` — не из `StatusText switch`.
- Для аварии внешнего источника строка меняется на явный аварийный текст, даже если предыдущий код был 3/4/5.
- При недостоверном статусе показывается отдельно диагностируемое состояние; нельзя оставить старый зелёный текст.
- Отображение PoweredOn (`equip.bucket.power`) продолжает существовать отдельно; цвет этого индикатора не рассчитывается из статусного кода.
- `StatusText` legacy-карточек и статическая палитра узлов/линий остаются без изменения.
- В tooltip статуса показывать `SignalId`, код (если валиден), качество/причину fallback и применённые UI-запреты. Не показывать технические адреса в пользовательском режиме, если это противоречит существующей политике интерфейса.

## 6. Рекомендуемый порядок и зависимости

```text
Этап 0 — исходная база
    ↓
Этап 1 — модель, DTO, миграция, validator, seed
    ↓
Этап 2 — чистый resolver
    ↓
Этап 3 — mapper, runtime state, карточка VM
    ↓
Этап 4 — UI-редактор и тесты редактора
    ↓
Этап 5 — интеграционная/регрессионная матрица
    ↓
Этап 6 — документация, сборка и полная проверка
    ↓
Этап 7 — независимое review, исправления, финальная проверка
```

Технически редактор (этап 4) может разрабатываться после этапа 1 параллельно resolver, но изменения общих DTO и mapper нельзя одновременно вести несколькими исполнителями без явного разделения владения файлами. Без специальной необходимости придерживаться указанного линейного порядка.

Каждый этап должен завершаться минимальными тестами, проверкой diff и явной фиксацией, что именно сделано. Не переходить к следующему этапу при красных регрессионных тестах текущего.

## 8. Финальные технические артефакты реализации

1. Коммиты/дифф кода модели, схемы, мигратора, resolver, runtime и UI-редактора статусов.
2. Тесты миграции, конфигурации, статусов, качества, приоритетов и командных запретов.
3. Обновлённая документация Route Map и SignalId (только изменившиеся контракты).
4. Отчёт проверки со списком изменённых файлов, командами и статусом PASS/FAIL/NOT RUN, изменениями поведения, оставшимися рисками и подтверждением отсутствия работ на реальном PLC.

**Условие завершения:** приложение на Mock и в безопасных тестах реализует настраиваемые статусы; все заявленные правила проверяются; изменения не затрагивают окончательную ответственность PLC за физическую безопасность.
